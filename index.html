App Foundry

Describe an app in chat and a coding agent builds it. One click publishes it live, and you can come back days later and keep editing in conversation.

Highlights

  • An isolated sandbox per app, each with its own coding agent and a live preview that updates as the agent edits.
  • Every edit is verified automatically. Checks run after each change, and failures go back to the agent to fix before you see them.
  • Safe publishing. Each release is an immutable build, so a failed publish changes nothing for users and rollback is instant, with no rebuild.
  • Idle sandboxes sleep and resume on demand, while published apps keep serving without them.

The architecture is right below, followed by the WhatsApp CRM, which runs on App Foundry.

How App Foundry is built

Editing happens in a sandbox; a published app is static files. Every path to data goes through the workspace database's row-level security.

  • Publishing is a pointer switch to an immutable build

    A build is uploaded first and goes live only when the pointer moves, so a failed publish changes nothing for users. Rollback moves the pointer back, with no rebuild.

    Trade-offRollback can't undo database migrations, so migrations have to be additive.

  • The AI agent acts as the person, under row-level security

    WhatsApp requests run with the sender's identity, so the agent can only see and change what that person could in the app. Reads are guarded and audit-logged; writes go through each app's own functions.

    Trade-offEvery app has to define its permissions properly, or the agent can't help.

  • One schema per app in a shared workspace database

    Apps in a workspace share core records like people and customers, but each app's own tables live in its own schema and can't alter another app or the core.

    Trade-offPreview and published apps share data, so a migration reaches users before the new frontend does.

  • Sandboxes exist for editing, not serving

    Idle sandboxes pause, then archive, and restore on the next edit. Published apps are static files, so they keep working while their sandbox sleeps.

    Trade-offThe first edit after a long break waits for the sandbox to restore.

WhatsApp CRM

The whole team updates one shared CRM by sending WhatsApp voice notes and business-card photos, so nobody types into a CRM and everyone stays on the same page.

What it does

  • Voice note in, structured record out. "Add this company, follow up Monday" in Hindi, English or Hinglish creates the company, contact, follow-up task and reminders for the day before and the day of.
  • Reports from chat. Ask "give me a revenue graph" on WhatsApp; the agent runs the queries, renders the chart on the server and sends it back in the same thread.
  • The AI only sees what you can see. The agent acts as the person who messaged it, under row-level security, and changes data only through vetted functions. Every query it runs is audit-logged.

Zavyo

A multi-tenant WhatsApp marketing SaaS with RAG chatbots and tool-calling AI agents, built on Meta's WhatsApp Cloud API. The company shut down before public launch.

Hard problems solved

  • Payments that never double-credit. An atomic compare-and-set claim lock makes Razorpay billing idempotent when webhooks and client verification arrive at the same time.
  • Tenant isolation everywhere. Enforced across REST, WebSocket and the vector layer, with a separate Qdrant collection per tenant and RBAC with 50+ permission keys.
  • No-code flows that run live. A stateful router executes ReactFlow graphs as real WhatsApp conversations, alongside agents with sales handoff, HTTP and follow-up tools.

How Zavyo is built

One FastAPI backend serves about 330 endpoints, a real-time inbox and every inbound WhatsApp message, with tenant isolation enforced at each boundary. It was built for a single-instance deployment, and the trade-offs below say where that shows.

  • Billing goes through an atomic claim lock

    A Razorpay payment can be confirmed by the webhook and the client at the same moment. One conditional update acts as compare-and-set, and success is judged by the modified count, so only one caller applies the credits. It guards all four payment paths.

    Trade-offA claim that crashes mid-apply is reclaimable only after a 10-minute stale window.

  • Tenant isolation at every boundary

    REST routes share one org-context resolver. WebSockets must pass a JWT check and a fresh database check. Inbound messages get their tenant from the receiving number, never the message. RAG uses a separate Qdrant collection per org.

    Trade-offScoping is enforced by convention in each layer. Next step: a repository layer where unscoped queries can't be written.

  • Flows compile to route maps, and stale sessions end cleanly

    ReactFlow graphs compile into block and route maps cached per org. The router notices when an admin changed or removed a bot mid-conversation and closes that session instead of replying through a bot that no longer exists.

    Trade-offThe router grew past 3,000 lines with sync database calls on an async path. Next step: split it and move to Motor.

  • Campaigns survive pause, stop and crashes

    Campaign status is re-checked before every contact, resumed runs skip contacts already sent, and final stats are reconciled so a resume never lowers the numbers.

    Trade-offNo rate limiting or 429 backoff yet, and WebSocket fan-out is single-process. Next step: a task queue with per-number limits, and Redis pub/sub.
